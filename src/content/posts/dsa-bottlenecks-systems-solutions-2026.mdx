> **核心观点：** DeepSeek Sparse Attention（DSA）并没有消除长上下文推理的资源瓶颈，而是重新分配了瓶颈：正式 Attention 的计算量下降后，Indexer、动态 KV Gather、缓存容量、跨设备传输以及 Runtime 调度成为新的性能边界。本文从执行路径出发，梳理十大瓶颈、现有研究、尚未解决的问题和可执行的实验设计。
>
> **范围说明：** 这里的 DSA 主要指 DeepSeek-V3.2 代表的、使用 Lightning Indexer 进行 token-level Top-k 选择的原生稀疏注意力架构。部分列举的工作针对更一般的 Block-sparse Attention，其思想相关，但并不代表已直接部署于原生 DSA。本文整理于 2026 年 10 月。

## 一、从 Dense Attention 到 DSA：瓶颈究竟转移到哪里？

传统 Dense Attention 在每次 Decode 时需要访问全部历史 KV。DSA 将这一过程拆成：**当前层 Hidden State → Lightning Indexer 全历史评分 → Top-k Selection → KV Gather / Swap-in → Sparse Core Attention**。

设历史上下文长度为 $L$，每个 Query 选择 $k$ 个 token。对于 Prefill，Dense Attention 的复杂度为 $O(L^2)$，而 DSA 的 Core Attention 为 $O(Lk)$；对于单步 Decode，前者为 $O(L)$，后者为 $O(k)$。**但 Indexer 仍然扫描完整历史**：它在 Prefill 的复杂度仍是 $O(L^2)$，在单步 Decode 中仍是 $O(L)$。实际常数依赖头数、向量维度和算子实现。

| 阶段 | Dense Attention | DSA Core Attention | DSA Indexer |
| --- | --- | --- | --- |
| Prefill | $O(L^2)$ | $O(Lk)$ | $O(L^2)$ |
| 单步 Decode | $O(L)$ | $O(k)$ | $O(L)$ |
| 历史 KV 的逻辑保留量 | 完整历史 | 完整历史仍可能需要保留 | Indexer 还需额外索引状态 |

对于一个层，逻辑上可将时延拆解为：

$$
T_{\mathrm{layer}} = T_{\mathrm{index}} + T_{\mathrm{topk}} + T_{\mathrm{gather}} + T_{\mathrm{attention}} + T_{\mathrm{other}}
$$

这里是依赖链的描述，并不表示优化后的各阶段一定严格串行。流水线、异步预取和融合 Kernel 会重叠其中部分时间。对分层存储而言，Gather 又包含命中匹配、未命中处理和 Host-to-Device 传输。

这一执行路径暴露出四个核心矛盾：**计算稀疏而索引未必稀疏；访问稀疏而存储不稀疏；访问位置动态确定而数据搬运希望提前进行；FLOPs 降低而 GPU 实际效率未必提高。**

## 二、DSA 的十大核心瓶颈

### 1. Lightning Indexer 的全历史扫描

**问题。** 传统 DSA 让正式 Attention 从全历史运算变成 Top-k 运算，却仍要对历史 Indexer Key 执行评分。上下文越长，Indexer 的占比越可能升高。在 IndexCache 论文的特定 200K Prefill 配置中，Indexer 占计算耗时的比例达到约 81%。这一数值属于论文的特定模型及测试条件，并不表示所有 DSA 负载都如此。

**现有方法。**

- **IndexCache**：用 Full Layer / Shared Layer 划分层组，让多数层复用相邻层的离散 Top-k 索引。论文在 30B 模型上报告最多省去 75% Indexer 计算、最高 1.82× Prefill 和 1.48× Decode 加速。
- **IndexShare**：在模型架构层面共享若干层的索引，降低重复评分。
- **HISA**：先按 Block 粗筛，再对候选 Block 做 Token 级精排，避免对完整上下文执行全部细粒度评分。其候选集合与原始 DSA 的选集高度一致，但并不意味着任意样本上严格一致。
- **MISA**：减少参与计算的 Indexer Head，用额外轻量决策降低评分成本。
- **PIVOT**：邻近 Query 共享一次全局前缀扫描，再为各 Query 细化候选；更适合 Prefill 或 MTP 中存在多 Query 的情况。

**遗留问题。** 层间索引复用、Query 分组和分层索引都在降低计算，但分别引入跨层选择差异、候选遗漏和额外中间状态。如何在长上下文及复杂任务中维持选择质量，是根本权衡。

### 2. KV 访问量下降，完整历史 KV 的容量却没有随之下降

**问题。** 假设上下文长度 128K、单步 Top-k=2048，当前步活跃比例约为 **1.56%**。但剩余 98.44% 的历史 token 并不能因为这一步未被选中就全部永久删除：它们可能在下一步、下一层或之后的生成过程中再次被访问。

因此，**访问稀疏不等于存储稀疏**。HBM 容量约束仍可能限制 Resident Batch、触发请求排队、降低设备利用率。

**现有方法。**

- **HiSparse（SGLang）**：HBM 只保留热 KV Working Set；完整历史保存到 CPU pinned memory；根据 Top-k 结果按需 Swap-in。
- **ECHO（OSDI 2026）**：将完整 KV 卸载到 Host Storage，结合 Graph-friendly Cache Manager 和预取；论文报告最高 2.1× 的长上下文生成吞吐增益。
- **ESS 等 Latent Cache Offload 工作**：进一步利用 CPU DRAM 承担大容量缓存。

**遗留问题。** HBM 压力减轻后，系统必须对未命中 KV 执行外部传输。缓存命中率、CPU 内存容量、传输带宽和同步延迟，取代纯 KV 容量成为新的限制。若进一步扩展到 SSD，还会出现读写干扰和随机 I/O 尾延迟。

### 3. Indexer → Top-k → Transfer → Attention 的串行数据依赖

**问题。** 原生 DSA 通常需要先利用当前 Query 完成打分与 Top-k，才能知道当前层应该加载哪些 KV。在纯 HBM 模式下，这体现为 GPU 内部算子依赖；在 HBM/DRAM 或 HBM/DRAM/SSD 模式下，会进一步成为外部数据传输处于关键路径的问题。

$$
\mathrm{Index}(h_l,K_l^I) \rightarrow \mathrm{TopK} \rightarrow \mathrm{LoadKV} \rightarrow \mathrm{Attention}
$$

**现有方法各有不同预测对象。**

- **ECHO**：利用评分阈值的可预测性，在 Indexer 尚未完全结束时提前识别高分候选，加载部分 KV；最终对预测未覆盖部分补齐，维持原有 Top-k 语义。
- **HiSparse + IndexShare**：已知一组层共享索引后，可以提前加载后续共享层相同位置的 KV；这种场景不需要预测新的 Top-k。
- **SparDA**：通过额外的 Forecast Projection 在当前层预测下一层所需的 KV Block，从而让下一层 I/O 与当前层计算重叠。注意它的主要验证针对其他 Block-sparse 架构，不是原生 DSA 上可直接套用的实现。
- **Janus**：针对多轮 Agent 的 Append Prefill，使用模型已有的 KV Selection Module，在较早的中间状态上预测 SSD 读取，并与计算重叠。

**遗留问题。** 并非预取命中率越高，端到端吞吐就一定越高。ECHO 的部分负载已具有 97%–99% 的 KV 缓存命中率，在这些条件下进一步增加 Decode 预取的收益有限。更应观察的是：**预取使多少实际暴露的 I/O Stall 离开关键路径？**

### 4. 稀疏 Token Gather 带来不规则访问及 GPU 效率下降

**问题。** Dense Attention 可以连续扫描 KV，DSA 却需要从分散的历史位置 Gather 离散 token。动态索引会产生内存请求分散、页表查找、布局转换、小粒度搬运和不均衡的 CTA / Warp 负载等问题。

即使理论 FLOPs 下降，实际 Memory Throughput、Tensor Core 利用率和 Pipeline Occupancy 也可能下降。ECHO 论文的一个 H20、64K 上下文、Batch=8 测试显示，Dense FlashMLA 与 Sparse FlashMLA 对应的计算资源利用率存在显著差距（约 97% 与 53%）；这不是对任意卡型或配置都成立的常数。

**现有方法。** Sparse FlashMLA、Paged KV Cache、融合 Gather + Attention、FP8 KV Cache、TMA 异步加载、Warp Specialization、在线 Softmax 融合与 Pipeline 调度。

**遗留问题。** Kernel 可以减少不规则访存的额外成本，却无法消除访问位置需要动态确定的事实。尤其当数据位于 PCIe 另一端时，这一问题还会叠加通信延迟。

### 5. Top-k Selection 成为新的算法和 Kernel 开销

**问题。** Lightning Indexer 输出全历史相关性得分后，还需要完成选择。得分张量物化、Kernel 启动、全局归约、候选排序以及 Kernel 之间的同步，都可能成为新的开销来源。

**现有方法。** cuDNN 提供面向 DSA 的优化 Top-k 和 Indexer/Top-k 融合策略。PIVOT 通过 Group Query 共用前缀扫描减少重复工作。

**遗留问题。** 单请求单 token Decode 未必具有可复用的多个 Query；Prefill、Chunked Prefill 和 MTP 则更可能从 Query 分组中获益。应区分单个 Top-k Kernel 的提速与端到端的提速。

### 6. Indexer 自身引入额外索引状态存储

**问题。** 除正式 Attention 的 KV Cache，DSA 还需要维护历史 token 的 Indexer Key。如果主 KV 已卸载到 DRAM，而 Indexer Key 也放到 DRAM，则全历史评分可能重新引入大量 PCIe 流量；如果 Indexer Key 留在 HBM，又会占用宝贵容量。

**现有方法。**

- **IndexCache / IndexShare**：减少执行 Indexer 的层数，并复用离散选择结果。
- **LatentIndex（2026 年 10 月）**：共享连续 Latent Index Cache，同时保留每层独立的选择能力，不强制多个层共用相同的离散 Top-k。在 DeepSeek-V3.2 的四层共享实验中，其逻辑 Indexer Cache 减少 61.1%；分层选择变体报告 2.30–2.72× 的 Decode Indexer 加速。

**遗留问题。** 索引状态共享与主 KV 压缩属于两个独立维度；即使减少了 Indexer Cache，也不会自动压缩全部历史 Attention KV。

### 7. 分层存储中的小粒度随机 I/O、缓存替换及放大

**问题。** DSA 需要的 2048 个 token 可能散落在很多不连续位置上。底层系统为了高效传输，通常更倾向于连续页或较大的 I/O 批次。这会产生：

| 症状 | 直接原因 | 可能的应对 |
| --- | --- | --- |
| 读放大 | 为少量有效 token 加载完整 Page 或 Block | 细粒度 Gather、页内重排 |
| 传输碎片化 | H2D 数据以大量小块形式请求 | 批量合并、向量化 Gather |
| 换入换出抖动 | Step 间活跃集合变化 | LRU、重要性与生命周期策略 |
| SSD 尾延迟 | 随机读、写入干扰、队列竞争 | DRAM 缓冲、读合并、写限速 |

**现有方法。** HiSparse/ECHO 使用 HBM 缓冲区管理与 GPU-side 命中检测；AVSG 研究向量化 Gather 与缓存管理；Janus 针对 SSD 将相邻读取合并、将分散页组织为更顺序的写入，并在读活跃时限制后台写入。

**遗留问题。** DRAM Offloading 与 SSD Offloading 并不等价。前者主要关注 PCIe 传输和命中路径；后者还需要考虑 IOPS、请求粒度、队列深度、尾延迟、读写干扰及持久化成本。直接替换存储后端无法构成完整的高性能三级缓存方案。

### 8. Prefill 与 Decode 的稀疏访问模式不同

**问题。** Decode 通常每请求每步只有一个 Query，更多关注 Step 间重叠；Prefill 或 Append Prefill 一次处理多个 Query，更关注它们所需历史 KV 的并集。

设一个追加 Chunk 有 $Q$ 个 Query，所需位置集合为：

$$
\mathcal{S}=\bigcup_{i=1}^{Q}\operatorname{TopK}(q_i)
$$

假设每个 Query 都有 $k$ 个有效历史候选，且最多从同一大小为 $L$ 的历史集合中选择，则：

$$
k \le |\mathcal{S}| \le \min(L,Qk)
$$

因此，虽然每个 Query 只关注 $k$ 个 token，整个 Chunk 的活跃 KV Working Set 仍可能大得多。

**现有方法。** ECHO 同时设计 Decode 的 Intra-query Prefetch 和 Prefill 的 Inter-query Prefetch；PIVOT 主要利用附近 Query 选择重叠；Janus 则着重优化 Agent 多轮 Append Prefill 中对 SSD 历史 KV 的加载。

**遗留问题。** 一个为 Decode 调优的 LRU + H2D Preload 策略，不一定适合 Append Prefill。在 Agent 场景中，KV 的跨轮次保留与临时复用又引入新的容量和传输权衡。

### 9. 多 GPU Context Parallelism 需要处理分布式 Top-k

**问题。** 当一个超长上下文分布在多个 GPU 上，每张 GPU 只存有部分历史 Key。原生全局 Top-k 需要合并本地候选分数或索引，然后决定全局被选位置，再进行必要的跨卡访问或聚合。

**现有方法。** Interleaved DSA（IDSA）等方法利用交错的数据分布和 Local Top-m 候选，减少全局选择的通信。核心思想是用受控冗余候选换取较少同步。

**遗留问题。** Local Top-m 并集不无条件等于原始 Global Top-k。如果追求模型原生选择的严格一致性，就必须额外处理选择正确性与通信成本的关系。

### 10. 动态 KV 管理与 CUDA Graph、调度器和 MoE 执行相互制约

**问题。** DSA 的活跃 KV 集合在每层、每步都可能变化；高性能 Runtime 却依赖固定 Shape、可复用缓冲区和 CUDA Graph 来降低 Host Launch 与同步开销。命中检测、替换、页表更新、Swap-in 若不断触发 CPU 控制流，会抵消稀疏计算优势。

**现有方法。** ECHO 的 Graph-friendly Cache Manager 将动态 KV 管理放入 GPU Graph；HiSparse 也采用融合 GPU-side 缓存机制，逐步适配 PD 分离、Prefix Cache、MTP 等特性。

**遗留问题。** 当 Attention 被优化之后，MoE、跨设备通信和 Runtime 固定开销可能跃升为主要瓶颈。DSA Serving 的瓶颈因此是动态的，必须做端到端分解，不能只看 Sparse Attention Kernel。

## 三、已有研究解决了什么？

| 技术路线 | 代表工作 | 首要目标 | 主要限制 |
| --- | --- | --- | --- |
| 层间索引复用 | IndexCache、IndexShare | 减少重复 Indexer | 层间选择可能不同 |
| 分层、分组索引 | HISA、MISA、PIVOT | 避免完整扫描和重复评分 | 候选遗漏或额外选择逻辑 |
| 连续索引表示共享 | LatentIndex | 降低 Indexer Cache 和计算 | 不减少主 KV 容量 |
| HBM/DRAM KV 卸载 | HiSparse、ECHO | 打破 HBM 容量墙 | PCIe、缓存命中与管理开销 |
| 跨层与查询预取 | ECHO、SparDA、HiSparse | 隐藏数据加载等待 | 收益依赖命中率与预测/共享关系 |
| SSD-centric 数据管理 | Janus | 隐藏 SSD 读取、改善随机 I/O | 负载和设备特性较强 |
| 稀疏 Kernel 优化 | FlashMLA、cuDNN | 降低 Gather、Top-k 和 Attention 开销 | 硬件及数据布局相关 |
| 分布式选择 | IDSA | 降低 Global Top-k 同步 | 近似选择与通信权衡 |

值得强调：**减少 KV 访问、减少 KV 存储、减少 KV 传输，是三个不同的问题。** 算法的理论稀疏比率不应直接等同于 HBM 节省比率或 PCIe 流量节省比率。

## 四、从系统研究角度看，哪些问题仍值得做？

### A. DSA 异步 KV 访问流水线

**矛盾：** Index Selection 决定 Data Access，导致 I/O 串行化。研究价值不在于再次用前一层 Hidden State 做一次普通预测，而在于证明现有 ECHO、HiSparse 等方法在哪些坏例下仍有无法隐藏的等待，并设计比它们更有效的访问流水线。

需要同时测量 **Exposed I/O Stall**、计算/传输重叠率、预取误差以及端到端 TPOT。高 Recall 本身不是系统贡献的充分证据。

### B. 跨层、跨 Step 的 KV Working Set 生命周期

**矛盾：** Top-k 告诉系统当前访问什么，却不直接说明下一次何时访问。不同 token 的生命周期可能具有短期密集、周期性、跨层一致或低频回访等模式。

可以考虑跨 Layer × Step 的复用距离、短中长期效用建模，以及面向不同存储层的数据布局。研究重点是比简单 LRU 更稳定地降低实际传输与 Stall，而不是只在离线 trace 上提高缓存命中率。

### C. HBM/DRAM/SSD 统一 KV 数据组织

**矛盾：** Token-level 稀疏访问与存储设备友好的 I/O 单位存在粒度错配。重点是如何在访问局部性、设备特性和运行时调度之间共同优化，而不是把 SSD 当作容量更大的 DRAM。

可探索的机制包括读取批次聚合、基于未来 Working Set 的 DRAM 缓冲、冷数据重新布局、异步写回及跨轮次状态复用。

### D. 面向 DSA 的请求调度

**矛盾：** Attention FLOPs 下降使单请求计算更便宜，但高并发下，HBM 容量和 Host I/O 带宽竞争可能更加突出。仅以 Batch Size 或 KV Token 总数调度请求，不能准确反映活跃 Working Set。

调度决策可以联合考虑缓存重叠、单请求预计传输流量、I/O 可隐藏窗口与延迟 SLO。

## 五、如何证明瓶颈真的存在：建议的实验

| 实验 | 自变量 | 主要观测指标 | 要回答的问题 |
| --- | --- | --- | --- |
| Indexer Scaling | 上下文 8K→1M | Index/Top-k 时间占比 | 稀疏 Attention 加速后谁成为主瓶颈？ |
| HBM Capacity Wall | 固定上下文，提升并发 | 最大 Resident Batch、吞吐 | 计算有空闲时是否仍被容量限制？ |
| Prefetch Bad Cases | 不同命中率、PCIe 带宽 | Exposed Stall、TPOT | 哪些 Miss 真正挡在关键路径上？ |
| Layer × Step Locality | 模型层、Decode Step | Top-k overlap、复用距离 | 是否存在可利用但未使用的前瞻窗口？ |
| Sparse Gather Efficiency | 不同候选分散度、Batch | Kernel latency、有效带宽 | 减少 FLOPs 是否造成访存效率下降？ |
| SSD Stress | 队列深度、读写比、DRAM 预算 | P99 I/O、读放大 | SSD 何时是瓶颈，DRAM 能隐藏多少？ |
| Prefill vs Decode | Cold / Append Prefill / Decode | TTFT、TPOT、KV Load | 不同阶段是否需要不同缓存策略？ |

实验应尽可能分开报告：

$$
T_{\mathrm{I/O\,exposed}}, \qquad T_{\mathrm{I/O\,hidden}}, \qquad T_{\mathrm{management}}
$$

如果未命中已被高度重叠，继续提高预取 Recall 很难得到大幅端到端收益；如果命中率很高却仍出现同步等待，瓶颈可能是碎片化搬运、Kernel Pipeline 或管理依赖。

## 六、结论

DSA 的系统演进可以视为三个阶段：

1. **从 Dense Attention 到 DSA：** 主要 Attention 计算下降，但 Indexer 与 Top-k 变得突出。
2. **从 Full-HBM 到分层 KV：** 解决容量墙，却引入 I/O、缓存替换与计算/传输串行依赖。
3. **从单请求优化到真实 Serving：** 多轮 Agent、百万级上下文、多 GPU 与高并发使全局数据组织和调度成为关键。

我认为最值得研究的总问题是：**如何把 DSA 的动态稀疏访问转化为存储层可提前规划、计算层可充分重叠、运行时可高效调度的数据访问？**

评估这样的系统时，不能只看 Attention FLOPs、Top-k Recall 或单一 Kernel 加速；最终应在质量约束、HBM/DRAM 容量约束和延迟 SLO 之下，衡量系统能够支持多少有效生成吞吐。
