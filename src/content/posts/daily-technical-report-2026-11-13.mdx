# 今日概览

本期以 2026 年 11 月 13 日（北京时间）为观察日，优先讨论 11 月 8—11 日公开的一手论文及 11 月 11 日的工程提案。经核验，最有价值的主线并非单纯提高算力利用率，而是**将 Agent 上下文、KV 传输、近似误差和推测状态纳入运行时决策**。以下论文均属于近七日补充观察，不冒充今日首发。

1. **Agent serving 的资源分配不能只看请求长度。** Evolving Infra 把 PD 节点角色调整与分布式 KV 管理解耦，利用 Agent 上下文变化指导缓存保留。
2. **KV 压缩开始引入可检验的误差预算。** VerKV 将常驻关键 token、全量 KV 的轻量摘要和按需回取结合，避免只依赖静态重要性判断。
3. **推测解码的训练目标需要对齐实际接受路径。** REAL Loss 直接优化期望接受长度，而非仅优化 token 级分布相似性。
4. **生成式推荐证明通用 LLM serving 不适用于所有自回归负载。** RecoGEM 通过业务 runtime 与执行 engine 解耦，适配短序列、大候选空间和严格尾延迟。
5. **开源讨论开始触及混合状态的正确性与稀疏索引的确定性。** vLLM 两项新 PR 分别处理 Mamba 推测解码状态边界和 sparse top-k 的排序不确定性；目前不能视为已发布能力。

## 重点进展

本期重点进展由四篇近期论文构成，分别讨论 Agent 资源调度、KV 回取、推测解码训练与生成式推荐服务。

## 核心论文与技术报告

### 1. Evolving Infra：Agent 自适应推理服务

**原始材料：** [Evolving Infra: Agent-Adaptive LLM Serving at Scale](https://arxiv.org/abs/2611.12304)，Hao Kang 等，2026-11-09 首次公开。

**解决的问题。** 传统 PD 分离假定 prefill/decode 资源比例可以根据较粗粒度的流量统计配置。但 coding、数学和 computer-use Agent 的上下文增长、输出长度与工具调用节奏差异明显；同一个 Agent 的压缩、分叉和子任务还会改变 KV 复用机会。论文特别指出，长时间未访问的上下文并不一定低价值：其 Claude Code 工作负载示例中，359 秒子 Agent 调用之后的 prompt 仍有 98% 可匹配历史 KV，而一次仅隔 12 秒的 compaction 后匹配比例为 14%。这两个数字是论文展示的具体观测，不应外推为所有 Agent 的规律。

**核心机制。** 作者把计算节点的 prefill/decode 角色和 KV 缓存位置拆开管理，使节点能够根据在线负载切换角色；规划器调节 PD 比例，Agent-aware 分布式 KV 管理器从上下文管理信号判断驱逐与传输。这样一来，计算资源的再平衡不必等同于缓存全部失效，缓存也不必仅依据最近访问时间驱逐。

**实验与证据。** 论文在 GLM-5.2、Kimi K2.6 和最高 256 张 GB300 GPU 的 coding、数学、computer-use 任务中，与 NVIDIA Dynamo 对比，报告平均端到端请求延迟最高降低 4.1 倍、P95 TTFT 最高改善 14 倍。这里的“最高”是不同实验条件下的最佳改善，并非普遍保障。论文另展示工作负载比例变化时固定 PD 划分可损失吞吐。

**限制与意义。** 其收益依赖可获取的 Agent 上下文管理信号、足够灵活的节点角色切换和集群规模；对于没有显式 harness 事件或上下文经常彻底重写的服务，适用性仍需验证。研究启发是：Agent runtime 的语义事件可能成为推理调度的第一类输入，而不只是外围日志。

### 2. VerKV：先验证误差，再决定是否回取 KV

**原始材料：** [Verify Before You Fetch: Reliable KV Cache Compression for LLM Inference](https://arxiv.org/abs/2611.11319)，Devanshu Jha 等，2026-11-08 首次公开。

**解决的问题。** 长上下文使完整 KV 难以常驻 HBM，静态压缩虽然减少数据传输，却不能保证每个后续 query 都仍适合此前的 token 选择。论文把问题从“如何找出永远重要的 token”转化为“当前 query 的近似注意力是否已达到指定误差容忍度”。

**核心机制。** VerKV 在 GPU 保留 query-agnostic pivotal tokens 和描述完整 KV 的 token-level sketch，完整缓存仍保留在 CPU。PoissonComp 负责抽样选择关键 token；推理时 KVFetch 利用当前 query 和 sketch 估计近似误差。若满足给定的 (ε,δ) 误差要求，则直接使用当前 GPU 数据；否则按 query 回取 CPU 中的额外 KV，逐步改善注意力结果。这里的保证针对论文定义的近似注意力误差，不等于最终生成文本或所有下游任务准确率的严格保证。

**实验与证据。** 在 Qwen3-4B、Qwen3.5-9B、Ministral-3-8B 的 32K 上下文实验中，作者报告 RULER/LOFT 平均任务质量达到稠密基线的 90%—100%，GPU KV 占用减少 8—32 倍，每个生成 token 回取的 CPU KV 为全量的 2%—23%，随模型变化。这些是作者在指定任务与模型上的实验结果，并非所有长上下文场景的统一指标。

**限制与意义。** 误差估计和动态回取自身具有计算、索引和 PCIe 开销；需要进一步评估高并发下的尾延迟、数据局部性以及极端 query 分布。其重要性在于把近似质量变成运行时可检查的条件，为分层 KV 系统提供更明确的“何时回取”接口。

### 3. REAL Loss：让 draft 训练真正对齐接受长度

**原始材料：** [REAL Loss: Optimizing Real Expected Acceptance Length for Speculative Decoding](https://arxiv.org/abs/2611.14399)，Yu Tian，2026-11-10 首次公开；[参考实现](https://github.com/King-ty/speculators/tree/real-loss)。

**解决的问题。** 推测解码的速度收益取决于 target 一次验证能够接受多少 draft token。传统交叉熵、KL 或 total variation 关注局部分布相似性；某些 block-level 目标虽尝试优化接受长度，却使用了与真实接受路径不完全一致的期望，从而可能产生梯度偏差。

**核心机制。** REAL 从实际接受分支出发构造期望接受长度的训练目标，采用路径权重进行无偏估计，并通过 Rao–Blackwellization 降低估计方差。作者强调修改的是 drafter 的训练损失，而非推理端的 draft 架构或验证流程。因此，它针对的是 draft 的训练质量，不是直接提出新的 GPU 验证内核。

**实验与证据。** 作者以 Qwen3.6-35B-A3B target 和 Domino drafter 进行受控 loss-level 对比，在 9 个任务子集、5 个随机种子上报告相对 WTV、VSD、DBLast 和静态 LK 基线更高的 probabilistic serving acceptance length。公开摘要没有提供可以直接转述为端到端吞吐加速的统一倍数，因此不将接受长度改善等同于真实部署的加速比例。

**限制与意义。** 训练损失改善仍需结合 drafter 推理成本、验证批量、内存压力与实际接受分布衡量净收益。该工作提示系统和训练协同优化应以真实执行路径上的效用为目标，而非仅优化代理指标。

### 4. RecoGEM：短自回归序列也需要专用 serving 运行时

**原始材料：** [RecoGEM: A Serving System for Production-Scale Generative Recommendation](https://arxiv.org/abs/2611.12296)，Xiangrui Yang 等，2026-11-09 首次公开。

**解决的问题。** 生成式推荐把候选物品选择变成自回归 token 生成，但其执行形态与通用对话不同：输出步数短、候选空间巨大、每一步选择直接处于关键路径，且要求极低 P99。直接复用以长序列生成和连续批处理为中心的 LLM serving 设计可能造成额外开销。

**核心机制。** RecoGEM 将候选状态转换、在线 artifact 更新等推荐特定逻辑放入独立 runtime，执行 engine 则针对可预测的短步长、候选选择和 attention 执行进行优化。它所体现的是业务状态机与通用计算引擎的边界重划，而非简单替换一个更快的 kernel。

**实验与证据。** 作者报告已在生产环境运行九个月以上，支持十余种生成式推荐模型；在其 OneModel 生产负载中，单实例超过 1000 QPS、P99 低于 35 ms，吞吐相对所选代表性基线提高 2.88 倍。不同模型、候选规模和服务硬件之间不能直接照搬这些指标。

**限制与意义。** 该结果高度依赖推荐负载的规则性和特定状态机，不代表对普通长上下文 Chat 的同等收益。它说明“自回归”只是表面共性，系统抽象还必须表达候选集、状态转换和服务等级目标。

## 开源项目的重要新闻

### vLLM：推测解码下 Mamba 状态的精确检查点（PR #67045）

[原始 PR](https://github.com/vllm-project/vllm/pull/67045)，2026-11-11 发起，检查时标记为 **Draft，尚未合并**。提案指出，混合 Mamba/Attention 模型在 speculative verification 时会为多个 draft 位置写入状态；若请求在已接受 token 中途遇到停止条件，或者异步调度还有在途 step，仅依赖“已计算 token 数”无法定位真正应该保留的 Mamba 状态。PR 引入可选的 truncate_acceptance_at_stop 等处理，以使 GPU 状态停在正确的请求终点。它影响 hybrid prefix caching 和状态恢复的正确性边界，而不是已经确认的性能提升。当前仍依赖前置 PR，不能视作生产默认行为。

### vLLM：稀疏 indexer Top-k 的确定性（PR #67044）

[原始 PR](https://github.com/vllm-project/vllm/pull/67044)，2026-11-11 发起，检查时为 **Open，尚未合并**。提案指出，sparse indexer 的 radix top-k 在使用 atomicAdd 分配输出槽位时，线程调度可能改变选中索引的顺序；在第 k 名附近存在相同分数时，甚至可能改变选中集合。提案通过可选确定性路径规范选中集合与顺序，意在提高可复现性和 batch-invariance。代价可能是额外排序、同步或计算，必须等待 PR 测试与合并结果；不可把“可复现”直接等同于“更快”。

## 前沿概念和技术

**Agent context signal。** 与普通请求级缓存热度不同，Agent 的 compaction、fork、subagent 调用、任务恢复会改变未来可复用的上下文。Evolving Infra 提供了将这些事件转为缓存决策信号的具体系统实例。未来的核心问题不是单纯记录这些事件，而是判断信号能否稳定预测复用，以及错误预测会造成多少迁移成本。

**Error-budgeted KV retrieval。** VerKV 展示一种“先估计误差、必要时补充数据”的路径。它与无条件加载全量 KV、固定比例压缩的差异，在于让每个 query 的数据需求动态决定数据移动；但误差保证的数学对象、运行时成本与任务准确率必须分别报告。

**Hybrid model state correctness。** Mamba 的递归状态与 Attention KV 的生命周期不同，推测解码又引入未必被接受的临时状态。vLLM PR #67045 表明，缓存键、checkpoint 边界和 stop 语义需要同时约束，不能只以 token 数量代表所有状态的有效版本。

## 深度分析

从四篇论文与两项工程提案可以观察到，运行时状态、质量约束与业务语义正在影响传统的计算和缓存决策。以下将其归纳为四条可检验的系统研究启示。

## 对大模型推理与存储优化的启发

第一，**缓存策略应从单一 recency 走向可解释的状态生命周期信号**。Evolving Infra 的工作负载观察说明“短时间间隔”与“高前缀复用”不是等价关系。评测时宜把 compaction、branch、tool gap 与真正的 KV 命中机会分开统计。

第二，**分层存储需要同时优化容量、带宽、误差和尾延迟**。VerKV 的条件式回取使“减少传输量”不再是唯一目标：还需要计算验证误差的开销、回取时延以及失败后的补偿成本。论文提供的是一个可研究的机制，不是对所有硬件配置的通用最优解。

第三，**性能优化必须以执行路径正确性为前提**。REAL Loss 提醒 draft 训练目标应匹配真实接受分支；vLLM 的 Mamba PR 则提醒运行时要准确保存被接受 token 对应的模型状态。训练目标与状态一致性分别位于两个层次，却共同决定推测解码能否可靠部署。

第四，**服务系统应暴露业务状态，而非仅暴露 token 数**。RecoGEM 和 Evolving Infra 的共同点是让 runtime 理解上层工作负载特征；差异在于前者面向生成式推荐的候选状态机，后者面向 Agent 的上下文管理。二者不应混成同一种负载模型。

## 今夜白的观察

本期材料形成一个值得跟踪的判断：推理系统优化的重点正在从静态的“每 token 计算效率”扩展到**对请求状态、上下文变更和近似质量的在线控制**。Evolving Infra 强调上下文事件驱动的资源规划，VerKV 强调 query 级的质量检查，REAL 强调训练目标与真实验证路径对齐，RecoGEM 强调应用运行时与计算引擎分层；vLLM 的两项 PR 则把正确性和可复现性带入这一链条。

尚未解决的问题同样明确：这些额外的控制与验证是否会在小 batch、短请求或高并发尾部造成不可接受的开销？上下文语义信号能否跨不同 Agent harness 泛化？混合状态的 checkpoint 与缓存复用能否形成稳定接口？后续应优先跟踪作者公开的消融实验、代码实现、跨硬件复测，以及相关 PR 的合并与回归结果，而不是仅看最佳加速数字。
