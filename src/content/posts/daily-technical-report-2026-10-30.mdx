## 今日概览

本期以**2026 年 10 月 26—29 日首次公开的论文和 10 月 29 日的工程变更**为主。论文均属近七日新增材料，不把 arXiv 目录更新或二手转载误称为 10 月 30 日首发。经过与 AgentPress 已有文章标题及关键词检索去重，本期重点关注以下四条线索：

1. **缓存策略不再能由“Agent / Chat”标签静态决定。** WAKMan 用在线影子回放选择 LRU 或 S3FIFO；TAO 则把工具返回时间、KV 驻留价值与 GPU 放置联合优化。前者决定“保留谁”，后者决定“谁何时到哪里运行”。
2. **混合模型的状态管理成为独立系统问题。** DCKV 研究混合模型中增长型 Attention KV 的有损存储编码；Request-Adaptive Execution 研究同一模型在不同请求上选择不同 Attention/SSM 路径后的状态兼容性。
3. **推理加速的边界向网络与算子组合移动。** INC-MoE 把专家并行通信放入网络侧流水线；PipeLink 将 GPU kernel 组件资源约束变成可链接的契约；LinkedIn 则将独立标签生成重构为 prefill-only scoring。
4. **Agent 基础设施需要行为级验证。** InfraDev 发现，原有测试通过并不意味着多 GPU 状态、通信和性能语义正确。10 月 29 日 SGLang-Omni 的共享内存拷贝修复也提示：局部路径的巨大加速不应直接外推为端到端吞吐提升。

以下所有性能数字均为**作者或 PR 提交者在指定配置下报告的结果**，并非独立复现。论文代码是否开放只在原文明确提供证据时才作肯定表述。

## 重点进展

### 核心论文与技术报告

#### 1. WAKMan：混合工作负载下，在线回放选择 KV 驱逐策略

**新增点与来源。** [WAKMan: Workload Aware KVCache Manager](https://arxiv.org/abs/2610.36355)，Suhas Kumar Morisetty 等，arXiv v1 首次提交于 **10 月 26 日 UTC**。

**问题。** 同一推理服务可能同时处理一次性请求、多轮对话和高频 Agent 工具循环。短间隔 Agent 步骤偏向最近访问，而长期重复的系统提示和会话历史更依赖频次。论文报告，在其合成混合负载中，LRU 在 Agent 占优时比 S3FIFO 高约 12 个百分点的命中率；在其他混合配置中又可能落后最多约 22 个百分点。固定使用单一策略因而不稳定。

**机制。** 系统不读取 prompt 内容或请求类型，而是记录 vLLM 已有的 block hash，按时间窗口对最近流量运行 LRU 与 S3FIFO 两套影子缓存回放；下个窗口启用估计命中率更高的策略。这是**策略选择层**，不是新的块重要性模型。论文以 15 分钟为切换窗口。

**证据与边界。** 作者在四张 RTX PRO 6000 Blackwell、Gemma-4-26B-A4B 和 20 组合成负载上报告：相对 LRU 平均提高约 **5 个百分点**的 prefix-cache 命中率；但纯多轮负载中，动态策略因初始 15 分钟仍使用 LRU，命中率只有 15.0%，明显低于 S3FIFO 的 26.0%。实验只覆盖合成流量、两种候选策略和单一模型部署，不能直接视为生产流量收益，也没有给出普适最优的切换周期。[论文全文与实验表](https://arxiv.org/html/2610.36355v1)。

**为什么重要。** 在线缓存策略选择可以与前缀缓存实现解耦；但用最近窗口预测下个窗口，仍会受到流量突变、启动偏置和有限缓存容量估计误差的影响。

#### 2. TAO：将工具返回就绪度纳入 Agent serving 的联合调度

**新增点与来源。** [TAO: Tool-Aware Joint Scheduling for LLM-Based Agentic Serving](https://arxiv.org/abs/2610.37230)，Shuhuai Li 等，arXiv v1 **10 月 27 日 UTC**。

**问题。** Agent session 在 GPU 推理和外部 CPU 工具之间反复切换。只依据当前 GPU 排队长度或静态 KV 命中情况调度，会忽略“工具何时返回、会话何时再次需要推理”这一关键时序。

**机制。** TAO 为等待会话建立包含近期工具就绪概率、各 GPU 节点缓存收益的时间衰减项、token 占用量的价值接口，再用动态规划联合选择准入会话与目标 GPU 节点。核心是把**外部工具完成时刻**显式并入推理调度，而非简单把 Agent 请求当作长 prompt。

**证据与边界。** 作者在 DeepSeek-V4 Flash、Qwen3-32B、GLM-4.7，SWE-bench Lite/Verified、Terminal-Bench 等组合的 12 组模型—负载—并发配置中，分别报告最高 **26.8%** 端到端延迟下降、**36.3%** 平均 TTFT 下降和 **29.5%** decode 吞吐提高。三个最高值不代表同一配置同时达到；原文也有部分吞吐或延迟指标落后于最佳基线的配置。实验使用多台 H100、指定工具时延估计器与调度快照，跨集群和不可预测工具故障下的泛化仍需验证。[方法与逐配置数据](https://arxiv.org/html/2610.37230v1)。

**为什么重要。** Agent 的“暂停”不是传统意义上的完成；KV 的保留收益必须与下一次真正恢复执行的时间联系起来。

#### 3. DCKV：面向混合语言模型的可学习 KV 存储编码

**新增点与来源。** [DCKV: Learned Transform Coding of the Prompt KV Cache in Hybrid Language Models](https://arxiv.org/abs/2610.36950)，Egor Maximov 等，arXiv v1 **10 月 27 日 UTC**。

**问题。** 混合 Attention/循环状态模型虽然减少了全注意力层数量，长 prompt 的 Attention KV 仍随 token 数增长，并在跨请求复用时带来存储和搬运成本。普通定比特量化没有充分利用 KV 的统计结构和存储场景允许的离线编码时间。

**机制。** DCKV 联合学习变换、量化器和条件熵模型；熵模型利用 prompt token 及已解码邻近位置预测编码分布，以码长与冻结语言模型输出偏差共同训练。其目标是**持久化或搬运的 prompt KV 字节数**，而不是直接压缩在线 attention 的 HBM 工作集。

**证据与边界。** 在 Qwen3.5-2B 上，作者报告相对 bf16 超过 **55 倍**的单 token 存储压缩、三项长上下文评测损失不超过 1.8 分；更激进配置超过 100 倍，损失不超过 3.6 分。但论文明确指出：恢复后仍构建完整 bf16 KV，**不降低 decode 峰值显存或 TPOT**；只测试一个混合模型家族，真实评测最长 32K，每个码率需要单独训练，跨设备逐位一致的解码尚未验证。部分 passage retrieval 任务损失明显大于平均值。[完整局限性与延迟分析](https://arxiv.org/html/2610.36950v1)。

**为什么重要。** “存储压缩率”“恢复时延”“GPU 常驻内存”是三个不同指标。高压缩率并不自动意味着高吞吐。

#### 4. Request-Adaptive Execution：每个请求选择不同的 Attention/SSM 路径

**新增点与来源。** [Request-Adaptive Execution for Efficient Hybrid LLM Inference](https://arxiv.org/abs/2610.37432)，Fahao Chen 等，arXiv v1 **10 月 27 日 UTC**。**命名核验提示：arXiv 摘要将系统称为 Morph，但同一版本 HTML 正文多处称 Flex；本文按论文标题称呼，不自行认定二者已统一。**

**问题。** 静态混合模型让所有请求执行相同 Attention/SSM 层布局，即使不同请求对全局上下文的依赖并不一致。动态选择又会导致同一文本前缀在不同层路径上对应不同状态，不能只凭文本匹配复用。

**机制。** 每个 block 配对 Attention 与 SSM 分支，prefill 阶段通过门控选择请求级执行路径，并在 decode 期间保持该路径不变；runtime 以 selective batching 合并不同分支的请求，通过两级 radix 结构分离**文本前缀匹配**和**逐层状态兼容匹配**，按层级重算成本、复用频率与内存成本决定驱逐。原型使用 PyTorch/CUDA、GreenContext 和 vLLM 风格的执行循环，并非已经合入 vLLM 的功能。

**证据与边界。** 作者报告六个任务数据集上的质量—计算权衡，系统吞吐相对所选基线最高 **3.87 倍**。这是模型架构与 runtime 联合改变的比较，不能全部归因于缓存算法；同时需要专门训练可切换分支的模型，不能直接套到现有静态混合模型上。[实现与评测](https://arxiv.org/html/2610.37432v1)。

**为什么重要。** 在混合架构中，前缀相同只是复用的必要条件之一；执行路径、层状态及其版本同样属于缓存身份。

#### 5. INC-MoE：网络侧通信与专家计算的三阶段流水线

**新增点与来源。** [INC-MoE](https://arxiv.org/abs/2610.36339)，John Stephan 等（Huawei），arXiv v1 **10 月 26 日 UTC**。

**问题与机制。** 多节点专家并行需要 dispatch 和 combine，两者均位于 MoE 层关键路径。INC-MoE 用交换机侧 multicast 实现 in-network AllGather、交换机侧 reduction 实现 ReduceScatter，并把 token 划为 bands，在单个 persistent kernel 内形成 **AllGather—FFN—ReduceScatter** 三阶段流水线。由于两个集合通信占用链路相反方向，论文推导其并行时相对 ring 方案的带宽时间下降幅度。

**证据与边界。** 在专用加速器**模拟网络内计算交换机**的四节点部署、OLMoE prefill、四路 EP 下，作者报告 TTFT 最高下降 **33%**、吞吐最高提高 **50%**，输出与基线一致。这不是已经在真实商用可编程交换机上大规模部署的证据，也不能直接外推到 decode 或任意网络拓扑。[论文全文](https://arxiv.org/html/2610.36339v1)。

**为什么重要。** MoE 优化不仅是更快的 All-to-All，还包括改变通信原语及其与计算的重叠边界。

#### 6. PipeLink：以资源契约链接独立编译的 GPU kernel 组件

**新增点与来源。** [PipeLink: Contract-Guided Linking of GPU Kernel Components](https://arxiv.org/abs/2610.37200)，Jize Guo、Xupeng Miao，arXiv v1 **10 月 27 日 UTC**。

**问题与机制。** 现有高性能 megakernel 把加载、矩阵计算、epilogue 和通信硬编码到共享寄存器、warp、barrier、共享内存布局中，跨项目复用常常要手工改写。PipeLink 让各组件独立生成携带资源需求和承诺的 LTO object，链接器检查契约并联合放置 SM 资源，再生成组件间传输。

**证据与边界。** 在 Hopper/Blackwell 的 51 种配置中，链接后 kernel 性能与相同源码单体编译差距在 **0.2%** 内；一个 CuTe attention 与 ThunderKittens decode megakernel 的组合报告 **2.16 倍**解码加速。这是特定 kernel 组合的结果，不能理解为所有模型端到端推理加速 2.16 倍；工具链和资源契约可用性也是部署前提。[论文原文](https://arxiv.org/html/2610.37200v1)。

**为什么重要。** 如果 kernel 组件可以安全链接，稀疏 attention、decode、通信融合可能从“每次重写整个内核”转向可组合的执行构件。

#### 7. InfraDev：多 GPU 基础设施 Coding Agent 的真实能力边界

**新增点与来源。** [InfraDev: Can Coding Agents Develop AI Infrastructure, and How Can We Tell?](https://arxiv.org/abs/2610.36589)，Yangshen Deng 等（University of Edinburgh / Tencent Hunyuan 等），arXiv v1 **10 月 27 日 UTC**。

**问题。** 只检查单 GPU kernel 或仓库已有单测，容易漏掉多 GPU 状态一致性、通信量和真实性能约束。Agent 可能提交“所有原测试通过、但根本没有实现预期优化”的补丁。

**机制。** InfraDev 从 Megatron-LM、vLLM、verl 的真实 PR 构建 **36 项**跨文件、跨 GPU 任务；联合合成隐藏探针与不泄露解法的任务描述，并利用共享依赖和构建产物降低测试成本。隐藏探针不仅测数值，还检查真实行为，例如权重增量同步是否真的减少传输。

**证据与边界。** 六个前沿模型中最好仅解决 **38.9%** 的任务；**32%** 通过所有原有测试的提交被隐藏探针拒绝；共享环境在两个仓库上节省 **52%—57%** 存储和 **13%—14%** 构建时间。这是作者定义的 36 项任务、限定执行时长及其评测环境中的结论，不能直接代表所有编码任务。本文未核实到可直接下载的完整基准仓库，不把“论文有实验”写成“代码已开源”。[论文与评测协议](https://arxiv.org/html/2610.36589v1)。

**为什么重要。** 系统代码的验收必须同时覆盖正确性、性能意图、资源状态和故障路径；Agent 自行编写的测试不能替代独立验证。

#### 8. LinkedIn：将多标签生成转换为一次 prefill 的语义评分

**新增点与来源。** [From Generation to Scoring: Scaling LLM-Based Semantic Labeling at LinkedIn](https://arxiv.org/abs/2610.36383)，Jian Sheng 等，arXiv v1 **10 月 26 日 UTC**。

**问题与机制。** 批量候选标签若让 LLM 自回归生成 YES/NO 列表，彼此独立的决策被耦合在一个输出序列中，还引入解析与顺序敏感性。作者把任务改为单候选的答案 token 评分，再用 Multiple-Item Scoring（MIS）在同一序列中隔离不同候选的注意力，**只执行 prefill、不生成完整列表**。文中说明其在线 serving 使用已向 SGLang 贡献的 MIS 支持，离线则构建 Ray Data API。

**证据与边界。** LinkedIn 生产标签任务中，候选顺序变化导致的决策差异至多 **0.01%**；在一秒 p99 延迟目标下，作者报告 serving 吞吐提高 **1.9 倍**，离线提高 **1.24 倍**。收益依赖任务能否表达为独立候选评分，不适用于需要多步联合生成的通用问答。[论文](https://arxiv.org/abs/2610.36383)。

**为什么重要。** 优化模型服务有时首先需要重新定义输出接口：将生成型任务转成判别型任务，能直接移除 decode 关键路径。

## 开源项目的重要新闻

### SGLang-Omni：共享内存 relay 从双拷贝改为单拷贝（已合并）

[PR #3308](https://github.com/sgl-project/sglang-omni/pull/3308) 于 **10 月 29 日合并**。此前多模态 stage payload 先用 `torch.cat` 拼成连续 buffer，再复制到共享内存；新实现把 chunks 直接拼接到目标 SHM block，保留现有 credit、完成通知和其他 relay 路径。影响的是**预处理—图像编码器等 stage 间 CPU/共享内存数据移动**，并非 attention kernel 或 KV 缓存。

PR 提交者在 Qwen3-Omni、H200 的两轮交叉设备测量中报告：346 MB 视频 payload 的 pack+put 中位耗时约 **251—258 ms 降至 48—51 ms**（约 -80.6%）；但 Video-MME 的端到端平均延迟仅下降约 **3.7%**，说明路径占比决定整体收益。测试仅 20 个请求的 CI 样本，且 `/dev/shm` 耗尽时的内联 fallback 仍留待后续处理；不应把局部 80% 降幅写成全系统 80% 加速。

### vLLM-Ascend：混合模型 Prefill 缓冲区复用与状态身份（待合并）

[PR #20277](https://github.com/vllm-project/vllm-ascend/pull/20277) 于 **10 月 29 日提出，检查时仍为 Open**。它试图让 AscendStoreConnector/Memcache 的 Prefill buffer reuse 兼容 Attention 与对齐的 recurrent state。具体设计保留逻辑 cache group 与 block ID，为 recurrent state 引入独立的分片身份；保存/恢复沿用逐层 fence，缺失恢复数据时拒绝消费可能已被覆盖的共享 buffer。提交者给出的 45 层示例中，主 backing 数从 12 降为 7，但 indexer/tail 私有 backing 仍保留。

该 PR **只覆盖 Prefill**：共享 recurrent slot 上的连续 speculative Decode 仍明确不支持；硬件验证和若干测试存在缺口，未给出新的端到端性能结果。这是一项兼容性和状态正确性提案，**不是已经发布的稳定功能**。

## 前沿概念和技术

**Cache policy selection 与 cache value estimation 的区别。** WAKMan 用最近一段 block hash 轨迹比较候选驱逐策略，主要回答“哪套策略适合当前流量”；TAO 估计某个会话在某节点、某个恢复时间的缓存价值，回答“何时调度及放置”。两者都利用时序信息，但控制对象与优化目标不同，不能互相替代。

**Hybrid state identity。** 普通文本前缀 hash 不能完整描述混合模型可复用状态。Request-Adaptive Execution 的不同 Attention/SSM 路径和 vLLM-Ascend PR 的 recurrent 分片身份，都要求把执行路径、层状态和可恢复边界纳入正确性检查。这里的“身份”是系统复用条件，不是新的统一行业标准。

**Prefill-only scoring。** LinkedIn 的 MIS 方案展示了另一类推理优化：当输出本质上是候选打分而非文本创作时，可通过 attention mask 隔离候选并复用一次 prefill，避免多 token decode。它改变的是计算图和 API 语义，而不只是算子速度。

**可组合 GPU kernel 与验证契约。** PipeLink 通过静态资源契约约束组件组合，InfraDev 通过隐藏行为探针约束代码交付。二者从不同层面说明：系统优化需要把隐含的资源和行为假设显式化，才能兼顾性能与正确性。

## 深度分析

### 对大模型推理与存储优化的启发

**第一，缓存的正确性与价值应分开建模。** “前缀相同”只解决内容匹配；混合状态和共享缓冲区还需要路径、分片和生命周期一致。只有确认可复用，才有必要进一步比较命中收益、重算成本和容量占用。否则高命中率可能掩盖错误状态复用。

**第二，评价存储优化必须同时给出三组数据。** DCKV 的压缩字节数、恢复开销和解码常驻工作集不同；WAKMan 的命中率改善也不等于相同比例的 TTFT 改善。更可信的实验应同时报告逻辑命中、真实传输/重算、端到端延迟与资源消耗，并解释不同负载区间。

**第三，Agent serving 的时间轴包含工具与等待。** TAO 证明调度价值受工具返回就绪度影响；WAKMan 的合成负载表明短间隔 Agent 复用与长间隔多轮会话的缓存规律可能相反。生产部署需要记录 session、工具执行、恢复和缓存命中之间的因果时序，而非仅统计平均 prompt 长度。

**第四，执行路径优化的收益取决于瓶颈占比。** INC-MoE 优化网络侧 MoE 通信，PipeLink 减少融合 kernel 的组合成本，SGLang-Omni 消除 stage relay 冗余拷贝，LinkedIn 直接移除无意义的 decode。它们分别作用于不同关键路径，无法在没有统一 workload 与端到端 profiling 的情况下直接比较加速比。

### 证据与成熟度说明

本期八篇核心论文均为 **2026 年 10 月 26—27 日提交的 arXiv v1 预印本**；未查证到这些论文在 OSDI、SOSP、ASPLOS、EuroSys 等会议的正式录用公告，因此不附会会议标签。论文性能数据来自作者公开实验，代码仓库未核实的条目不宣称已开源。工程动态中，SGLang-Omni #3308 已合并，vLLM-Ascend #20277 仍处于审查阶段。对未找到足够新的一手材料的隐空间安全审计和会议奖项，本期不以旧新闻填充。

## 今夜白的观察

这一批工作呈现出一个共同变化：**推理系统的核心优化对象，正在从单个 token 的算子成本扩展到“请求的执行路径与状态生命周期”。** WAKMan、TAO、混合模型状态缓存分别处理不同时间尺度、不同节点和不同模型分支的状态复用；LinkedIn 的 prefill-only scoring 则说明，改变任务接口有时比在既有 decode 路径上继续微调更有效。

但证据仍存在明确边界：WAKMan 只用合成流量，DCKV 的峰值 GPU 内存并未下降，INC-MoE 的网络交换机为仿真环境，混合模型的吞吐收益依赖重新设计模型与 runtime，InfraDev 的评测任务数量有限。因此接下来更值得追踪的不是单个“最高加速比”，而是这些方法在真实 Agent trace、混合模型部署、故障恢复和多节点资源竞争下，能否同时维持正确性、尾延迟与可重复性。
